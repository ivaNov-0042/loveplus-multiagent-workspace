### 第三节：位流层收尾——码本等价性判定与判据勘误

下午到傍晚，把「46 字节 → 640 个频谱系数」这条链彻底收口。

**表全部坐实**（地址见 `reverse_code_bin.md` §5e）：`mlt_quant` 0x8bcf58（Q12，行距 16 字，
÷4096 后与 FFmpeg 浮点表偏差 ≤0.0006）、标准偏差表 0x801d34（Q12×54）、差分码树 0x8bbb38
（行 0 全零占位，行 i = FFmpeg 行 i-1 的前 46 值，逐值吻合）、噪声常数 0x8bf98c（3 值 Q15）。
另发现 `index_table` 的定点替身：0x801e54（行长−1 = 13,9,6,4,3,2,1,1）与 0x801e74
（2¹⁵/行长 的倒数表，编译器生成的整除）。

**判定性实验**（新脚本 `scripts/loveplus/siren14_framecheck.py codebook`）：游戏码树是堆式布局
（结点 n 的子 = `tree[2n]`/`tree[2n+1]`）、码字拆解按行长整除且 digit0 落在末位，与 FFmpeg
「值即下标 + 幂掩码」表面完全不同。枚举全部 1276 条比特路径比较分量元组：**7 个类别
100% 一致**（181/94/48/520/209/192/32）。⇒ 游戏只是同一标准码本的另一种存储，
**`.spp` 流是标准 G.722.1 流**，既有 FFmpeg 派生移植可直接用（只需改 28 region / 640 / 32 kHz）。
这个结论把任务 1.3 的范围砍掉一半：不必重写表。

**判据勘误**：我最初设计「一帧解完必须正好用掉 368 bit」作为判据，**不成立**——编码器不
填满帧，实测帧尾留 0~21 bit（40 帧里只有 8 帧恰好填满）。已把判据换成码本等价性；
`bits` 子命令保留做「解码不跑飞」的回归检查（两套约定在 40/40 帧上都不越界）。

**自己犯的错**（记录以免重犯）：① 位读器把「已读位数→字偏移」写成 `bit_index>>3`，应为
`(bit_index//16)*2`；② 符号位计数没按码字重置（`nz` 跨码字累加）；③ `mlt_quant` 行距按
16 **字节**读了（应为 16 **字**/64 字节）。三处都表现为「位消耗超支」，正是我前面判据设计
不当会掩盖的那类错。

**与 FFmpeg 的真实差异**（写报告要写明）：① FFmpeg 无 28-region 分支；② 噪声幅度本作按
类别取单一平台值（0.17678/0.25/0.70711），FFmpeg 按区域非零系数个数索引 21 元表；
③ 本作有「可用位数上限 320·(nregions/14) + 超出部分 5/8 压缩」（18400 bps 下不触发），FFmpeg 无。

剩余：变换层（`0x76b67c` 及下游 0x76d000-0x76f000，VFP 密度 34-36%）未做；移植版参数化与
报告未做。

### 第四节：变换层还原（定点）与「频域混音」的发现，外加一处勘误

**变换层定位**：`0x1420dc`（848 B，整帧流水线）在第 0x1423bc 处唯一调用 **0x76b67c**，
后者内部调 **0x75dd2c**（IMDCT）。两者都是**定点**（i16 乘 + `>>13/14/15` + `0x7fff` 饱和），
不是浮点——上一轮把 VFP 密集的 0x76d000-0x76f000 当作变换层，**勘误**（见下）。

- `0x75dd2c` = 快速 IMDCT，640 = 10×2⁶（320 支为 10×2⁵）：前置蝶形（符号决策取自位模式表
  0x8bf8fc/0x8bf924）→ log2 级基 2 蝶形 → 10 点逆 DCT-IV 核（表 0x801eb4，Q15，
  阶梯步长 5）→ 旋转级（表 0x8bf974，Q14）。
- **窗表三张**（0x802954 / 0x802e54 / 0x803354，各 640 i16 = 320 个 (sin,cos) 对）：
  逐项拟合 `G·(sin φ_j, cos φ_j)`，**最大偏差 ≤ 0.99 LSB**，G = 18317（≈0.5590·2¹⁵），
  φ 步长 π/640（320 支）与 π/1280（640 支）⇒ 就是 MLT 正弦窗
  `w[k] = G·sin((k+0.5)π/1280)`，与 FFmpeg 的 `sinf((i+0.5)*M_PI_2/320)` **同形**。
- `0x76b67c` = 窗 + 重叠相加（TDAC 旋转），50% 重叠、hop 320、每帧 640 样本，
  把新尾 memmove 进调用者缓冲给下一帧 —— 与 FFmpeg `vector_fmul_window` + `imdct_prev` 同构。

**意外的收获**：整帧流水线 `0x1420dc` 显示引擎在 **MLT 系数域混音**——32 个 voice 槽各自解码出
640 个系数（`0x142454` → `0x75e69c`），按 `vol·gain` 定点乘后**加进同一个系数缓冲**，
最后整帧只做一次 IMDCT/声道。线性变换下这等价于时域混音，但省掉 N 次变换。
同一段代码还给出 `step = 帧长×14/16 = 560`（= 20×28）的累加长度，**独立印证了 §5e 的
「位流只编码 560 个系数、其余 80 个为 0（14 kHz 带宽上限）」**；且本作每帧 memset 整个 640
系数缓冲，而 FFmpeg 把多余的 40 个槽位留着上一帧的陈旧值——**移植时要按本作清零**。

**勘误细节**（避免下次再踩）：0x76d000-0x76f000 无 `push{…,lr}` 序幕、全仓无 `bl` 指向它，
只被函数指针表 0x76bc34（在 0x76bb14 内）间接调用，而 0x76bb14 的调用者全在 0x765xxx，
0x765xxx 又只被 0x64xxxx-0x66axxx（SE/BGM 引擎）调用。⇒ 那片浮点代码属于别的编解码器/音效内核。
教训：**「VFP 密度高」不是「属于语音链」的证据**，判定归属要顺着调用图走
（BL 扫描 + 函数指针表扫描 + 调用者窗口），不能只看指令类型分布。

遗留：移植（28/640/32 kHz/5-bit + 清零尾部 + 速率控制守卫）、解码验证（内部一致性，无原始 PCM 参照）、
报告；另有 0x76d000-0x76f000 归属哪个编解码器未查（与本任务无关）。

   ③FFmpeg siren.c 的折叠·旋转排布在不翻转时与本实现逐样本一致（~2e-7）。取负版本是另一条
   信号（互相关 ≈ 0.005），属 FFmpeg 通用逆 MDCT codelet 的输入约定，不作判据。
   残留：本作定点 IMDCT 的旋转级符号未逐样本对照。

## 踩坑

- **「按数值反查池字」对 >0xfff 的结构体偏移无效**：编译器用 `mov rX,#0x1440` 或

  正确做法是**按 imm12 反查指令**（`add` 的 imm12 = 值经 ROR 编码，本例 0x34000→0x90D、0x34c00→0xBD3）。
- 序幕扫描（只匹配含 lr 的 push）会漏掉**不保存 lr 的叶子函数**（如 `0x742668`、`0x742638`），
  会误判成「调用点落在别的函数体内」。
- `pdg` 对以 `b`/尾调用跳转的**跳板**（如 `0x722034 → b 0x71eed4`）只给两行；
  真身要用 `findbl`/`pd` 顺藤摸瓜，别以为函数就这么短。

### 思路转换：从「顺着调用链爬」改成「拿参考实现的常量表反查」

上一轮卡在「逐帧解码核心在哪」——顺着 0x6d99e8 → 0x72314c → 0x71e164 爬，越爬越偏（那些都在
命令队列与引擎侧）。这轮换了两个手法，都一击命中：

1. **大结构偏移别按数值反查池字**（0x34098/0x34c18 在池里根本不存在），要按 **imm12 反查指令**：
   `add rX, rY, #0x34000` 的 imm12 是 **0x90D**、`#0x34c00` 是 **0xBD3**（0x34000 = 0x0D ROR 18）。
   据此找到 7 处 `add #0x34c00`，其中 **0x68c944** 正是往 `obj+0x34c18` **写解码器对象指针**的地方：
   解码器对象**不是堆分配**，而是**静态内嵌**在驱动对象 `obj + 0x4000 + i*0x800 + 0x98`。
2. **拿 FFmpeg `siren.c` 的整数表当字节模式全仓搜**（`find_code_xref.py` 反查引用池）：
   `vector_dimension` → 0x75e688/0x75e68c、`number_of_vectors` → 0x76639c、`expected_bits_table`
   → 0x75c4fc/0x75c7d4。**G.722.1 实现库 = 0x75c000-0x767000** 当场确定。

### 本轮结论（细节进 `reverse_code_bin.md` §5d）

- **帧解码入口 = `0x75e69c`**（56 行 C）。它就是**位读器 + 帧结构解析**：`param_3==0xe(14) ? 4 bit : 5 bit`
  是速率控制字段宽度；循环体是 **MSB-first 位读器**（16 位字用尽取下一个 u16）——
  与既有 memory 记的「16 位小端字内 MSB-first」**完全吻合**。
- 三个子函数依次是 `0x75e0c0`（envelope：读 5 bit 后 **−7**，= `esf_adjustment=7` ✓）、
  `0x75c3dc`（categorize，用 `expected_bits_table`）、`0x75e2b8`（decode_vector，用
  `number_of_vectors`/`vector_dimension`）。**与 FFmpeg 的 `siren.c` 结构逐项对应**。
- 位流封装层 `0x142454(ctx,ch,frame,out)` = 喂一帧 → `0x75e69c` → 拷进 `dec+ch*0x500+0xa08`
  （**0x500 B = 1280 B = 640×u16**，再一处 640 证据）。
- 变换（MDCT）在 `0x76b67c`，下游 0x76d000-0x76f000 是全区 VFP 密度最高带（34-36%）→
  **位流/量化层定点、变换层浮点**。

### 与 FFmpeg 参照的差异（重要，供 1.3 用）

- 我们从 jsdelivr 取到了 `FFmpeg/libavcodec/siren.c`（872 行，`raw.githubusercontent.com` 在本机不通，
  jsdelivr 与 git.ffmpeg.org 通）。它 **`#define FRAME_SIZE 320`、`REGION_SIZE 20`、
  `s->number_of_regions = 14` 写死**，`rate_control = get_bits(gb, 4)`、`rate_control_possibilities = 16`。
  → **FFmpeg 只有 14-region 那一支**；本作两支都有（14/28 ↔ 320/640，与 `dec+0x144c`/`dec+0x1464` 一致）。
- 好消息：FFmpeg 标准路径用**包长**算可用位数（`init_get_bits8(gb, avpkt->data, avpkt->size)`），
  `sample_rate/50` 只用于 MS 变体与校验 → **18400 bps 这种自定义码率本来就能解**，
  不用改算法，只要把 region 数/变换长度/速率控制位宽参数化。
- 所以「既有 `siren14.py` 解不出正确音频」的根因是**参数化错**（16 kHz 那支），不是算法缺失。

### 第三节：位流层收尾——码本等价性判定与判据勘误

下午到傍晚，把「46 字节 → 640 个频谱系数」这条链彻底收口。

**表全部坐实**（地址见 `reverse_code_bin.md` §5e）：`mlt_quant` 0x8bcf58（Q12，行距 16 字，
÷4096 后与 FFmpeg 浮点表偏差 ≤0.0006）、标准偏差表 0x801d34（Q12×54）、差分码树 0x8bbb38
（行 0 全零占位，行 i = FFmpeg 行 i-1 的前 46 值，逐值吻合）、噪声常数 0x8bf98c（3 值 Q15）。
另发现 `index_table` 的定点替身：0x801e54（行长−1 = 13,9,6,4,3,2,1,1）与 0x801e74
（2¹⁵/行长 的倒数表，编译器生成的整除）。

**判定性实验**（新脚本 `scripts/loveplus/siren14_framecheck.py codebook`）：游戏码树是堆式布局
（结点 n 的子 = `tree[2n]`/`tree[2n+1]`）、码字拆解按行长整除且 digit0 落在末位，与 FFmpeg
「值即下标 + 幂掩码」表面完全不同。枚举全部 1276 条比特路径比较分量元组：**7 个类别
100% 一致**（181/94/48/520/209/192/32）。⇒ 游戏只是同一标准码本的另一种存储，
**`.spp` 流是标准 G.722.1 流**，既有 FFmpeg 派生移植可直接用（只需改 28 region / 640 / 32 kHz）。
这个结论把任务 1.3 的范围砍掉一半：不必重写表。

**判据勘误**：我最初设计「一帧解完必须正好用掉 368 bit」作为判据，**不成立**——编码器不
填满帧，实测帧尾留 0~21 bit（40 帧里只有 8 帧恰好填满）。已把判据换成码本等价性；
`bits` 子命令保留做「解码不跑飞」的回归检查（两套约定在 40/40 帧上都不越界）。

**自己犯的错**（记录以免重犯）：① 位读器把「已读位数→字偏移」写成 `bit_index>>3`，应为
`(bit_index//16)*2`；② 符号位计数没按码字重置（`nz` 跨码字累加）；③ `mlt_quant` 行距按
16 **字节**读了（应为 16 **字**/64 字节）。三处都表现为「位消耗超支」，正是我前面判据设计
不当会掩盖的那类错。

**与 FFmpeg 的真实差异**（写报告要写明）：① FFmpeg 无 28-region 分支；② 噪声幅度本作按
类别取单一平台值（0.17678/0.25/0.70711），FFmpeg 按区域非零系数个数索引 21 元表；
③ 本作有「可用位数上限 320·(nregions/14) + 超出部分 5/8 压缩」（18400 bps 下不触发），FFmpeg 无。

剩余：变换层（`0x76b67c` 及下游 0x76d000-0x76f000，VFP 密度 34-36%）未做；移植版参数化与

## 第四节：变换层还原（定点）与「频域混音」的发现，外加一处勘误

### 第四节：变换层还原（定点）与「频域混音」的发现，外加一处勘误

**变换层定位**：`0x1420dc`（848 B，整帧流水线）在第 0x1423bc 处唯一调用 **0x76b67c**，
后者内部调 **0x75dd2c**（IMDCT）。两者都是**定点**（i16 乘 + `>>13/14/15` + `0x7fff` 饱和），
不是浮点——上一轮把 VFP 密集的 0x76d000-0x76f000 当作变换层，**勘误**（见下）。

- `0x75dd2c` = 快速 IMDCT，640 = 10×2⁶（320 支为 10×2⁵）：前置蝶形（符号决策取自位模式表
  0x8bf8fc/0x8bf924）→ log2 级基 2 蝶形 → 10 点逆 DCT-IV 核（表 0x801eb4，Q15，
  阶梯步长 5）→ 旋转级（表 0x8bf974，Q14）。
- **窗表三张**（0x802954 / 0x802e54 / 0x803354，各 640 i16 = 320 个 (sin,cos) 对）：
  逐项拟合 `G·(sin φ_j, cos φ_j)`，**最大偏差 ≤ 0.99 LSB**，G = 18317（≈0.5590·2¹⁵），
  φ 步长 π/640（320 支）与 π/1280（640 支）⇒ 就是 MLT 正弦窗
  `w[k] = G·sin((k+0.5)π/1280)`，与 FFmpeg 的 `sinf((i+0.5)*M_PI_2/320)` **同形**。
- `0x76b67c` = 窗 + 重叠相加（TDAC 旋转），50% 重叠、hop 320、每帧 640 样本，
  把新尾 memmove 进调用者缓冲给下一帧 —— 与 FFmpeg `vector_fmul_window` + `imdct_prev` 同构。

**意外的收获**：整帧流水线 `0x1420dc` 显示引擎在 **MLT 系数域混音**——32 个 voice 槽各自解码出
640 个系数（`0x142454` → `0x75e69c`），按 `vol·gain` 定点乘后**加进同一个系数缓冲**，
最后整帧只做一次 IMDCT/声道。线性变换下这等价于时域混音，但省掉 N 次变换。
同一段代码还给出 `step = 帧长×14/16 = 560`（= 20×28）的累加长度，**独立印证了 §5e 的
「位流只编码 560 个系数、其余 80 个为 0（14 kHz 带宽上限）」**；且本作每帧 memset 整个 640
系数缓冲，而 FFmpeg 把多余的 40 个槽位留着上一帧的陈旧值——**移植时要按本作清零**。

**勘误细节**（避免下次再踩）：0x76d000-0x76f000 无 `push{…,lr}` 序幕、全仓无 `bl` 指向它，
只被函数指针表 0x76bc34（在 0x76bb14 内）间接调用，而 0x76bb14 的调用者全在 0x765xxx，
0x765xxx 又只被 0x64xxxx-0x66axxx（SE/BGM 引擎）调用。⇒ 那片浮点代码属于别的编解码器/音效内核。
教训：**「VFP 密度高」不是「属于语音链」的证据**，判定归属要顺着调用图走
（BL 扫描 + 函数指针表扫描 + 调用者窗口），不能只看指令类型分布。

遗留：移植（28/640/32 kHz/5-bit + 清零尾部 + 速率控制守卫）、解码验证（内部一致性，无原始 PCM 参照）、
报告；另有 0x76d000-0x76f000 归属哪个编解码器未查（与本任务无关）。

## dpb 作用域与保真分档核查（回应提问）

用户提问「dpb 是不是所有音频解码都要用？有没有可能是高低保真的语音各自采用？」——静态核完，结论落进 `reverse_code_bin` §5h。

要点：

- dpb 只服务 Siren14 语音链（唯一消费者 `0x68b950` → `0x68b174` → `0x142568`；`0x142568` 全仓只有一个调用者 `0x68b1d8`），BGM/SE 走各自的 CSTM/CSAR 容器头。
- `0x142568` 本次实读：`bits/帧 = bitrate/50`；`rate_param = 7000 << dpb[1]` 只认 7000（14 region / 320 样本 / 16 kHz）与 14000（28 / 640 / 32 kHz），其它值跳 `0x124730` 报错；对 `dpb[0]` 不做校验 → 分档能力存在，粒度是音库级。
- 本作 base dpb = `{23,1,1,16}`；92655 条 size 全是 46 的倍数、`.spp` 被 46 整除 → 单帧长单配置。
- 卡带 RomFS 名表（UTF-16，~4.60 MB）只有一套 Siren14 三件套，无 `Siren14VoiceEx.*` → SoundEx 那套 dpb 属追加データ，不在卡带。
- 跨作品核对：New Love Plus 与 New Love Plus+ 两个 ROM 里，按 dpb 形状扫全盘，唯一成立的 dpb 都是 `{23,1,1,16}`（+版 @747015024、前作 @965856128）。
- 逐帧保真变化来自 5 bit 速率控制，实测最长三条每帧有码 region 数 24–28、中位 28 → 本库几乎每帧满 28 region。

方法留档：3DS RomFS 文件名是 UTF-16LE（ASCII 搜不到），用「UTF-16 名表拿 (dataOffset,size=16)」+「dpb 形状扫全盘 + 配套 .bin 索引结构反解数据区基址自校验」两步可定位任意 ROM 里的 dpb。脚本留在 `/tmp/02_static-re/scan_dpb.py`（未入正式 `scripts/`，方法已写进 §5h）。

另：确认用户要的 WAV 范围＝已生成的 15 条最长语音（`data/loveplus/nlp_plus/decoded/long/`，16-bit 单声道 32 kHz），不批量导出其余条目。
