## 二、关键成果

### 1. `conditionvoice_<0|1|2>.lmb` = 条件语音索引表

- 卡带 PACK 归档里共 33 个 `.lmb`，其中 `conditionvoice_{0,1,2}.lmb` 是语音索引表。
- 这些文件是 **zlib 压缩流**（`78 9c` 开头）。注意：PACK 条目的 `Flags bit0` 并未标记为压缩，必须自行判断——这是 PACK 提取器的一个坑。
- 解压后：`@0x00` u32 = 记录数（207），随后是 **12 字节定长记录**：

```
struct LMBRecord {   // 12 字节
    u32 flag;        // 高16位 = 条件组 id（0x0001, 0x0104, 0x0105 ... 严格递增）
                      // 低16位 = 组内序号（1,2,3 ... 严格连续，31/31 组全部验证通过）
    u32 _mid;        // 恒为 0
    u32 voice_id;    // Siren14voice.bin 直接索引；同组内严格 +1 递增
};
// 相邻记录之间以 flag == 0xFFFFFFFF 的记录作分隔
```

⚠️ 字段顺序坑：`voice_id` 是**第三个** u32，不是第二个。最初按 `(flag, voice_id)` 解出全 0，浪费数轮。

### 2. 用户假设「一段对话里多个音频索引是连续的」——已量化验证成立

实测 `conditionvoice_0.lmb`：

| 条件组 | 条数 | voice_id 区间 | 连续 |
|---|---|---|---|
| `0x0104` | 5 | `0x2a16–0x2a1a` | ✅ |
| `0x0105` | 5 | `0x2a1b–0x2a1f` | ✅ |
| `0x0106` | 3 | `0x2a20–0x2a22` | ✅ |
| `0x0107` | 3 | `0x2a23–0x2a25` | ✅ |
| `0x0108` | 3 | `0x2a26–0x2a28` | ✅ |
| `0x0109` | 3 | `0x685a–0x685c` | ✅ |

**同一条件下的一组语音，其 voice_id 是连号排列的。**
→ 对中文配音极有利：**替换一整段对话 = 替换一段连续 id 区间**，改动范围清晰可控。

三个文件结构完全同构（均 207 条 / 31 组，seq 编号逐位对齐），仅 voice_id 基址不同：

| 角色 | 主音库段 | 次音库段 |
|---|---|---|
| 宁宁 Nene | `0x2a16`–`0x2a6a` | `0x6859`–`0x68b6` |
| 凛子 Rinko | `0x9821`–`0x9875` | `0xd656`–`0xd6b3` |
| 爱花 Manaka | `0x1069e`–`0x106ea` | `0x1442e`–`0x1448b` |

每个条件组在两个音库段之间**交替取值**，像是同一角色的两套录制批次/情绪录法。

### 3. `Siren14voice.bin` 索引表验证（决定性）

```
741240 B = 92655 条 × 8 字节 (offset u32, size u32)
offset 100% 单调递增（92654/92654）
off + size 全部落在 .spp（687534906 B = 655.7 MiB）内，0 越界
size == 0 仅 1 条（尾哨兵）
```

`conditionvoice` 的所有 voice_id **全部 in-range**，例如：

| voice_id | .spp offset | size |
|---|---|---|
| `0x2a16` | 56,661,098 | 11454 |
| `0x2a28` | 56,920,906 | 10810 |
| `0xd656` | 380,283,288 | 13524 |

### 4. 定位到疑似「语音引擎」音库（短片段连续流）

按 size（时长）分段统计整个语音库，发现三个**硬性上限极低**的区段：

| 区段 | id 范围 | 条数 | size | 时长(16kHz G.722.1) |
|---|---|---|---|---|
| bankA | 0–5147 | 5148 | 690–3128 B | **43–196 ms**，均值 123 ms |
| bankB | 28270–32997 | 4728 | 506–2944 B | **32–184 ms**，均值 109 ms |
| bankC | 56413–61631 | 5219 | 598–2944 B | **37–184 ms**，均值 119 ms |
| *普通对白对照* | 40000–44000 | 4000 | 138–38364 B | *9–2398 ms*，均值 388 ms |

时长换算依据：G.722.1 @16 kHz，320 字节 = 20 ms 帧；`.dpb` = `0x17, 1, 1, 0x10`，其中 `0x10` 与 16 kHz 吻合。

三个独立结构特征共同指向「固定槽位的原子片段音库」：
1. **硬性时长上限** ~196 ms —— 普通对白可达 2.4 s，这些绝不超过 0.2 s
2. **字节连续流**：区内 0 个 offset 间隙（5147 / 4727 / 5218 条链接全部首尾相接）
3. **全部 size 为偶数**（2 字节对齐），均值约 6 帧

结合「游戏内需要读出玩家名字」这一功能需求，判定为**姓名/音节合成音库**：
每个槽位是一个 mora / 音节 / 极小语素，引擎拼接若干槽位拼读姓名。

**待验证**：尚未解码听音；槽位语义（假名？音节？语素？）、三个 bank 与三位角色的对应关系均未坐实（三 bank 条数 5148/4728/5219 并不相等，弱证据不支持「一角色一姓名库」的简单读法）。

## 四、文本数据（真实台词已解出）

- `.mdc` 邮件词典，含**明文 UTF-8 日文**。记录格式：`0x00 <len u8> <UTF-8 len 字节> 0x00`，记录间用 `0xffff` + `c1/c2/c4/c8/d0/e0/f0` 标志簇 + `00` 填充。该标志簇低字节为**一热编码桶号**（`c1→c2→c4→c8→d0→e0`，单 bit 上移），第 4 字节 `ff/fe` 为配对奇偶位，尾部 `01/02` 为段号 → 多级连续索引结构。
- 解出台词量：`maildic_n` **598** 条 / `maildic_m` 571 条 / `maildic_r` 552 条；`worddic_*` 各 31 条。
- 样例：`おはよう、起きて？`、`調子はどーお？`、`コラ！居眠りしちゃダメだぞ。ふふ`、`夜遅くにごめんね`

## 五、格式结构体（已坐实，附踩坑点）

### PACK 容器（复刻自 gdkchan/NLPUnpacker `Program.cs`）
```
@0x00 'PACK'
@0x04 u32 FileCount = 值>>16
@0x08 u32 StringPointersOffset (+Base)
@0x0C u32 StringTableOffset    (+Base)
@0x10 u32 DataOffset           (+Base)
@0x14 u32 DecompressedSectionLength
@0x18 u32 CompressedSectionLength
@0x1C u32 Padding
@0x20 + i*0x20 条目(0x20B): sig[4], unk0, DecompressedLength,
        DecompressedOffset(+Base), unk1, Flags(bit0=IsCompressed),
        CompressedLength, CompressedOffset(+Base)
文件名 = *(StringPointersOffset + i*4) → StringTableOffset + 偏移, NUL 结尾
```

### SERI 文件（原 `.yaml` 的自定义二进制编码）
```
@0x00 'SERI'
@0x04 u32  -> ValuesOffset = 该值 + 4      ← 不加 BaseOffset
@0x08 u16  ParametersCount                ← 是 @0x08，不是 @0x0A（易错）
@0x0A  ParametersCount * { u16 NameOffset, u16 ValueOffset }
TypesTable @ ValuesOffset - ParametersCount   （每参数 1 字节类型码）
Values      @ ValuesOffset
类型码: 's'=str  'i'=int32  'f'=float  'b'=bool  'a'=array  'h'=nested-array
```
⚠️ 必踩两个坑：
1. **字符串（参数名与 's' 值）解析在 PACK 容器的 StringTableOffset（ROM 缓冲）里**，不在 SERI 文件内。我最初拿文件自身缓冲索引 → 参数名全空。
2. `ValuesOffset` 严格用 `@0x04 + 4`，再多加会错位。

## 正确结论（已验证）

实测**语音库全部 clip 的 size 都能被 46 整除**（bankA 5148 条、bankB 4728、

→ 真实帧长 = **46 字节**，即 16 kHz G.722.1 的「45 字节载荷 + 1 字节帧头」。

## 教训

引用编解码器理论参数前必须先用数据验证帧长（找 size 的最大公约数 / 整除因子），
否则会凭空差一个数量级。今后遇到「按采样率×位深×帧长」推算时长，
一律先跑一遍「所有 size 对候选帧长的整除性」，再决定用哪个帧长。
